# D28：向量化改为后端进程内运行（ONNX Runtime + EmbeddingGemma 300M），去掉 Ollama，统一 768 维

- 状态：已采纳（取代 D15；计划 `docs/plans/2026-11-18-onnx-embedder.md`，需求 R50）
- 日期：2026-11-18

## 背景

D15 用 compose 里的 Ollama 运行 Qwen3 向量模型（0.6B，1024 维），经网关调用。用了一个多月后，用户觉得它"太大、太耗性能"（2026-11-18）。在这台 Mac 上实测：

- Ollama 镜像 4.23 GB，加上模型 610 MB，共 4.84 GB；多两个 compose 服务（`ollama`、`ollama-init`）。
- 模型加载后容器占 2.0 GB 内存（空闲 5 分钟后自动卸载，降到 121 MB）。
- 容器里只能用 CPU：文档入库每秒 1.05 段，单条问句 54 毫秒。

大头是 Ollama 这个运行外壳，不是模型本身。ONNX 是通用的模型文件格式，ONNX Runtime 是只负责"运行模型"的引擎；后端镜像里本来就装着它（解析文档的 markitdown 依赖的 magika 带进来的，1.20.1），分词库 tokenizers、numpy 也都在。

用户还要求顾及多语言（记忆和资料里中文、英文及其他语言都会出现）。

## 先行验证（2026-11-18）

在后端镜像起的临时容器里（4 核 CPU，每批 2 段，与项目设置一致）比较了 6 个 ONNX 候选和现有模型。两套测试集：A 是手写的 64 条记忆（中、英、日、韩、西、法、德）和 73 个换了说法的问句；B 用项目自己的中文文档生成，396 段，用"文档标题 + 小节标题"找正文。

| 方案 | 磁盘 | 内存（加载后 / 入库峰值） | 入库 | 单条问句 | A 第 1 名 | A 前 5 名 | B 前 5 名 |
|---|---|---|---|---|---|---|---|
| 现在：Ollama + Qwen3 0.6B | 4.84 GB | 2.0 GB | 1.05 段/秒 | 54 ms | 93.2% | 100% | 35.4% |
| **EmbeddingGemma 300M（4 位量化）** | **207 MB** | 327 / 459 MB | 2.1 段/秒 | 17 ms | **95.9%** | 98.6% | **47.2%** |
| gte-multilingual-base（8 位量化） | 341 MB | 774 / 988 MB | 5.4 段/秒 | 6 ms | 87.7% | 95.9% | 34.3% |
| Qwen3 0.6B 的 ONNX 版（8 位量化） | 596 MB | 1.1 / 1.3 GB | 1.4 段/秒 | 32 ms | 86.3% | 95.9% | 31.3% |
| granite-embedding-97m-multilingual-r2 | 117 MB | 282 / 367 MB | 15.3 段/秒 | 22 ms | 68.5% | 91.8% | 25.5% |
| multilingual-e5-small | 129 MB | 433 / 541 MB | 13.6 段/秒 | 2 ms | 61.6% | 75.3% | 29.8% |
| bge-small-zh-v1.5（只懂中文，对照） | 23 MB | 50 / 163 MB | 22.9 段/秒 | 1 ms | 42.5% | 63.0% | 29.0% |

- 100 MB 级的小模型不够用，跨语言尤其差：e5-small 有很强的"同语言偏好"，中文问句会把所有中文记忆排在英文记忆前面，"中文问、英文记忆"11 题全错。
- 同款 Qwen3 换成 ONNX 的 8 位量化版反而掉分，体积和内存也没省多少。
- 无关问句测试（15 个不该召回任何记忆的问句）：门槛 0.3 时，EmbeddingGemma 保留 98.6% 的正确记忆、挡掉 86.7% 的无关问句；现有模型只能挡掉 20%（它的合适门槛约 0.41）。所以换模型后 `knowledge.recall_min_similarity` 的默认值 0.3 不用改。

局限：测试集小、是自己写的；B 故意出得难，只适合看相对高低；只测了向量这一路（知识库搜索还会合并关键词结果）；每个模型只测了一种量化版本。

## 备选方案

1. 维持 D15（Ollama + Qwen3）。
2. 只换轻的外壳：模型不变，用 llama.cpp 的服务镜像代替 Ollama。
3. 做成可选：不装向量模型时只走关键词检索。
4. 改用云端向量模型（需求池 R11）。
5. 后端进程内用 ONNX Runtime 跑 gte-multilingual-base（Apache-2.0）。
6. 后端进程内用 ONNX Runtime 跑 EmbeddingGemma 300M（Gemma 使用条款）。

## 结论

采用方案 6（用户 2026-11-18 决定，接受 Gemma 使用条款）。

- **模型**：`onnx-community/embeddinggemma-300m-ONNX` 的 4 位量化版（`onnx/model_q4.onnx`、`onnx/model_q4.onnx_data`、`tokenizer.json`），固定到提交 `5090578d9565bb06545b4552f76e6bc2c93e4a66`，三个文件的 SHA-256 写在代码里，下载后校验。项目里的模型名是 `embeddinggemma-300m-q4`。
- **运行**：新的 `Embedder` 实现 `OnnxEmbedder`，在后端进程里用 ONNX Runtime（只用 CPU）运行；第一次用到时才加载，计算放到线程里，不挡事件循环。`adapters.embedder` 的默认值改为 `onnx`。
- **向量统一 768 维**（原 1024）：表结构改一次，现有条目的向量清空，后端启动后在后台用新模型重新算（每次启动都补还没有向量的条目）。
- **前缀归向量化实现管**：EmbeddingGemma 的查询和文档都要加各自的前缀（查询 `task: search result | query: `，文档 `title: none | text: `）。`Embedder.embed` 增加参数说明这批文字是查询还是文档，知识模块不再自己拼前缀（修订 D15 的"前缀写在知识模块里"）。
- **模型文件不进仓库、不进镜像**：放在 `.workdata/models/embeddinggemma-300m-q4/`。后端启动后在后台检查：文件齐全且校验通过就不联网；缺了或校验不过就下载（先写临时文件，校验通过再改名，不会留下半个文件）。下载期间和没联网时后端照常能对话；下载失败（没联网、网络抖动）后隔 1 分钟、5 分钟、之后每 15 分钟自己再试，下好以后知识库就能用、不用重启；大小对但校验不过的旧文件在重新下载前先删掉，不会被加载（与原来 `ollama-init` 下不下来时的表现一致）。下载地址可用 `EMBEDDING_DOWNLOAD_BASE` 换成镜像站，因为有哈希校验，换地址不影响安全。不单独起一个下载用的 compose 服务：少一个服务，首次启动也不用等下载完才能对话。
- **去掉 Ollama**：compose 删掉 `ollama`、`ollama-init` 和数据卷 `ollama-models`（剩 `postgres`、`litellm`、`backend` 三个服务）；默认模型清单删掉 `embed-qwen3-0.6b`，模型来源删掉"本机 Ollama"；已有安装在启动时把网关里这个模型删一次。已有安装里原来的 Ollama 容器、数据卷和镜像不会自动删（程序不替用户删数据）：升级后它们还在、容器还在运行，确认新的向量模型能用后按使用指南第 2 节的三条命令手工清掉，能腾出约 4.8 GB。
- **经网关的实现保留**：`LiteLLMProxyEmbedder` 和模型页对向量模型的支持不删，端到端测试继续用它配假网关。以后要换云端向量模型（R11）不用改代码，但不是只改一项，要做四件事：① `.env` 里设 `ADAPTERS__EMBEDDER=litellm_proxy` 和 `KNOWLEDGE__EMBEDDING_MODEL=<网关里的向量模型名>`；② 默认的模型来源里已经没有向量模型的来源，要在 `.env` 里用 `MODELS__SOURCES` 加一个（`mode` 为 `embedding`；这一项是整份清单，原有的“公司 LiteLLM 网关”也要一起写上），重启后到模型页用它新增向量模型；③ 模型要输出 768 维（不是就报错，不会写进库）；④ 旧向量是另一个模型算的，要清空（`UPDATE knowledge_items SET embedding = NULL`），再重启后端，它会在后台重新算。
- **用量照常记录**：`OnnxEmbedder` 每次计算后报告 token 数与耗时，调用方仍是"向量化"。

对其他决策的影响：

- **D01（模型调用统一走网关）**：向量化是例外。它在进程内运行、不出本机、不花钱，不需要网关的转发、密钥管理和限流；对话模型仍然全部走网关。
- **D13（第三方服务一律由 compose 管理）**：不冲突。ONNX Runtime 是进程内的库，不是服务。
- **D15**：被本决策取代。

## 原因与代价

- 磁盘从 4.84 GB 降到 207 MB，少两个服务、一个数据卷；模型加载时的内存从 2.0 GB 降到 0.33～0.46 GB；入库快一倍，单条问句快两倍。
- 准确度不降：记忆问答与现有模型持平（差 2 题，样本小，不能说谁更好），中文文档和小语种明显更好；用现有门槛 0.3 就能挡住大部分无关问句。
- 不新增安装的包：`onnxruntime`、`tokenizers` 已经在环境里，只是登记为直接依赖并锁定现有版本。
- 代价：**许可**。EmbeddingGemma 用的是谷歌的 Gemma 使用条款，不是标准开源许可：可以免费使用，但有使用限制，再分发时要附带条款。所以模型不进仓库和镜像（`make bundle` 打的包里也没有，和原来 Ollama 的模型一样要在目标机器上下载或手工拷贝 `.workdata/models/`），README 写明来源与条款链接。以后不想受这类条款约束时换方案 5（gte-multilingual-base，同为 768 维，不用再改表，重建向量即可）。
- 代价：空闲时多占内存。Ollama 空闲 5 分钟会卸载模型（容器只占 121 MB）；进程内的模型加载后常驻，后端多占约 330 MB。暂不做空闲卸载，真有需要再加。
- 代价：入库时会用满 CPU（原来 Ollama 也是），时间缩短了一半。
- 代价：首次启动要从 Hugging Face 下载 207 MB；这里的网络单连接只有约 50～100 KB/s，所以下载用多连接分段（实测约 600 KB/s，5 分钟左右）。
- 代价：现有条目的旧向量作废，升级后要重新算一遍（按每秒 2 段，1 万段约 80 分钟；期间这些条目只能按关键词搜到）。升级前先 `make backup`；要退回只能恢复备份。
- 代价：ONNX Runtime 锁在 1.20.1（magika 带来的版本），已验证能跑这个模型；以后升级 markitdown 时要回归向量化。
