# D18：审批与预算刹车的实现方式

- 状态：已采纳
- 修订：预算刹车部分被 D23 取消（2026-10-19）；审批的实现方式仍有效，审批的范围改为按会话权限档位（D23）。
- 日期：2026-10-16（M4 实施计划，用户审阅后按方式二执行）

## 背景

设计文档 7.5 写了审批的四种选择（同意、修改参数后执行、拒绝、回复一句话），10.5、10.8 写了暂停与恢复、预算刹车，但没说清几处细节。写计划前先做了实验（结论在 `docs/plans/2026-10-16-m4-mcp-and-approvals.md` 的先行探测表里），据此定下四件事。

## 结论

1. **"回复一句话"用带 message 的拒绝实现**，不用设计文档第 20 节写的 `respond`。
   - langchain 1.4 里 `respond` 的意思是"人替工具给出结果"：工具没执行，工具卡片却显示成功，容易误以为做了。
   - 改成拒绝这次调用，并把用户的话以"用户回复：……"转给智能体；卡片显示"已回复：……"。
2. **MCP 工具默认看服务的只读声明**（MCP 协议的 `readOnlyHint`）。
   - 规则文件里没写到的 MCP 工具：服务声明只读的自动执行，其余按 `mcp_default`（默认"先问你"）。
   - 这样接入一个新服务时，不用逐个工具写规则，查询类工具也不会一直打扰你。
   - 代价：声明由服务自己写，写错了（把写操作声明成只读）会被自动执行；不放心的服务可在规则里写 `"<服务名>_*": ask`。
3. **预算刹车用 LangGraph 的 interrupt，"停止"就是停止这次运行**。
   - 2026-10-18 修订：只按调用次数刹车，去掉"最多花多少美元"这条上限（用户决定界面只统计 token、不显示费用）。
   - 与工具审批走同一套暂停、恢复、重启后再审批的流程，前端也是同一种卡片。
   - "继续"在恢复时追加一份额度；"停止"调用停止运行的接口，运行记为"已停止"，用量保留。
   - 恢复时按暂停那一刻的状态重建预算，节点重新执行时会走到同一个 interrupt。
4. **有运行正在进行时拒绝"重新加载"**。
   - 重新加载要关掉旧的 MCP 连接，正在跑的运行会突然调用失败。
   - 等待审批的运行不挡重新加载，但工具或审批规则变了，它的审批就作废（最终审查后修订）：`approval.required` 带着暂停时的指纹，恢复时对不上就拒绝，提示停止后重新发消息。否则按新规则重新判定时，"拒绝"了的调用可能因为不再需要审批而照样执行。
   - 重启后 MCP 服务还在连接时提交审批：先等连接完成（最多 75 秒）；连不上就按"变了"处理。

## 代价

- 第 1 条与设计文档第 20 节的写法不同，以本记录为准。
- 预算（调用次数上限）在 `config/app.yaml` 里，改了要 `make restart` 才生效；"重新加载"只重读 MCP 服务清单与审批规则。
- 第 2 条的只读声明由服务自己写：以后接入远程（网络型）MCP 服务时，"只读"的网络工具（如搜索）的参数也能把数据带出去，被提示词注入诱导的模型可能借此外传；接入这类服务时建议在规则里写 `"<服务名>_*": ask`（最终审查提出，记在这里提醒）。
