# D21：管理页面直接改配置——workdata 叠加配置，模型走网关的模型管理接口

- 状态：已采纳（2026-10-18 用户决定，第 3、7 条按建议定）
- 修订：第 1、2、6 条被 D22 取代（2026-10-19：配置进数据库与 .workdata，去掉叠加）；第 7 条按 D23 只在前两档权限下成立。
- 日期：2026-10-18

## 背景

管理页面（设计文档 2026-10-18-frontend-admin-ui-design.md）的纯界面已做完（交付方式 A）。用户选交付方式 C：模型、技能、MCP 三页读写都接上。设计文档第 9 节列出了五个与现有部署冲突的地方：配置目录只读、技能目录只读、密钥只在 `.env`、后端没有容器控制权、改模型要重启网关。

## 备选方案

- **配置怎么变成可写**：
  - 去掉 `config/`、`agents/skills/` 的只读挂载——不选：D20 审查时特意改成只读，防止一条被同意的命令改动代码与审批规则。
  - `workdata/` 下放同名文件，整份替换 `config/` 的——不选：在页面上改过一次之后，项目自带配置的更新（新的默认服务、默认规则）再也看不到。
  - `workdata/` 下放同名文件，**按条目叠加**——采用（用户决定）。
- **模型改完怎么生效**：
  - 写 `workdata/config/models.yaml` 再重启网关——不选：后端在容器里，没有权限重启网关容器。
  - 后端与网关合进一个容器、宿主机另跑一个小助手、把 `docker.sock` 挂给后端——不选：分别是结构大改、多一个常驻程序、等于给后端整台机器的权限。
  - **网关自带的模型管理接口**（打开 `STORE_MODEL_IN_DB`，模型存进网关的数据库）——采用（用户决定），不用重启网关。

## 结论

1. **只读目录不动，可写的放进 `workdata/`**（用户决定）：
   - `workdata/config/`：`mcp_servers.yaml`、`approval_rules.yaml`、`app.yaml`（**只认 `agent.default_model` 一项**，其余设置项一律忽略：被同意的命令改得动这份文件，不能让它改主机名白名单、技能目录等）、`skills.yaml`（停用了哪些技能）；
   - 这几份文件手改写坏了：后端照常启动，用 `config/` 的设置；MCP 页、模型页显示原因；技能停用清单写坏时先当作没有停用；页面上的修改被拒绝，不覆盖用户的文件；
   - `workdata/skills/<技能>/`：上传的技能；
   - 模型不放这里（见第 3 条）。
2. **加载规则**（用户决定）：先加载 `workdata/`，`config/` 只是兜底的基础配置；两边有同名文件时都读，同名的条目以 `workdata/` 的为准。细则：
   - MCP 服务同名时按字段覆盖（用户条目里写了的字段为准，没写的沿用自带的；所以停用自带服务只要写 `enabled: false`）；审批规则按工具名覆盖；技能按文件夹名区分；
   - 设置类（`app.yaml`）按设置项逐项覆盖，没写的沿用 `config/`；
   - 停用自带的条目 = 在 `workdata/` 里写一条同名的、只标成停用（自带的删不掉）；你自己加的可以真删；
   - **新上传的技能不允许与已有技能同名**（包括自带的），所以技能不存在覆盖；
   - 页面只写 `workdata/`；改完立即生效：MCP 与审批规则沿用设置页已有的"重新加载"，技能本来每次运行都重读。
3. **模型走网关的模型管理接口**（用户决定）。先行验证（2026-10-18，网关 v1.105.0，临时网关 + 测试库 + 本机模拟的上游，不花钱）的结论：
   - 新增（`POST /model/new`）后立即能调用，`/model/info` 里能看到（`db_model: true`），网关重启后仍在；删除用 `POST /model/delete`。
   - **修改 = 先按新内容新增一份、再删掉旧的**：`PATCH /model/{id}/update` 能改值，但它是合并写入，传 null 也去不掉已有的参数（二次验证：关掉"思考"后 thinking、max_tokens 仍留在网关里）。删旧的失败时把新的也删掉，不留同名的两份；两份同时存在只有一瞬间，两份都是有效配置。
   - 深度思考（`thinking`）、输出上限（`max_tokens`）原样转发给上游。
   - **价格要写在调用参数里**（`litellm_params.input_cost_per_token` / `output_cost_per_token`）；写在模型信息里会被丢掉。
   - **与自带模型同名时网关不会覆盖，而是两份一起分摊调用**（负载均衡）：后端在调网关前自己拒绝重名。
   - **自带模型（`config/models.yaml`）网关不让改、也不让删**：页面上自带模型只读、标出"自带"，改它们照旧编辑 `config/models.yaml` 后 `make restart-gateway`（用户确认）。这是第 2 条"同名以 workdata 为准"的例外：模型做不到覆盖自带的，页面上新增的模型也不能与自带的同名。
   - 网关把调用参数加密存进数据库，加密用 `LITELLM_SALT_KEY`（没设时用主密钥）：启用前在 `.env` 设一个固定的 `LITELLM_SALT_KEY`，之后不能改；恢复备份时要用同一个值。
   - 默认对话模型写进 `workdata/config/app.yaml`。**向量模型只读**（用户决定）：换向量模型要把整个知识库重新向量化（R31）。
4. **密钥本轮不改**（用户决定）：
   - 新增模型只引用 `.env` 里已有的密钥（写 `os.environ/UPSTREAM_GATEWAY_KEY`，网关调用时替换，验证可用），页面上不填密钥；
   - 需要密钥的 MCP 服务照旧：在 `.env` 设置、在 compose 的 `backend.environment` 传入、配置里写 `${变量名}`；页面只提示要设哪个变量；
   - 以后考虑把密钥存进 PostgreSQL（R32）。
5. **后端仍不持有容器控制权**：交付方式 C 用不到；系统页（R28）时再定。
6. **备份**：`workdata/config`、`workdata/skills` 加进备份的文件目录；网关数据库（`litellm` 库）本来就在备份里。
7. **被同意的命令能改动可写配置**（用户确认按建议处理）：
   - 智能体执行的命令和后端在同一个容器里（D20），`workdata/` 对它可写；Mac 共享目录不区分用户，靠文件权限挡不住。
   - 于是一条被同意的命令能改审批规则（例如把"执行命令"改成自动执行）、往 MCP 清单里加一个本地服务（后端下次启动或重新加载时就会运行它）、放进一个技能。
   - 这和 D20 已接受的风险同一类（被同意的命令本来就能读写数据库里的全部对话与运行状态），但审批规则是唯一的把关，被改掉的后果更重。
   - 处理：
     - "执行命令每次先问"写死在代码里，`workdata/` 里的规则放宽不了它；
     - 以后整理成单一容器时，用 Landlock 一类机制把命令能写的范围限制在会话目录与缓存里（R33）。

## 原因与代价

- 原因：不改只读挂载，项目自带的配置仍随代码版本管理；用户的改动全部在 `workdata/` 与网关数据库里，跟着备份走；模型改动立即生效，不需要容器控制权。
- 代价：
  - 配置有两处来源，排查时要两边都看：页面上每条标出"自带"或"你加的"；
  - 自带模型在页面上只读；
  - 页面加的模型只在网关数据库里，`LITELLM_SALT_KEY` 丢了或改了，这些模型就读不出来；
  - 见第 7 条的安全代价。
