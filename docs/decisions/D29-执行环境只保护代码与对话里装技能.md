# D29：执行环境只保护程序代码；带基础工具、能装包；对话里能装技能

- 状态：已采纳（修订 D20、D23、D25 与设计 2026-10-23 的 5.1；需求 R51）
- 日期：2026-11-19（用户决定）

## 背景

用户在对话里让智能体安装一个 GitHub 上的技能，智能体没有去试，直接回答“沙箱无法联网、`/skills/` 只读、不能装包”。核对后：

- “不能联网”是错的：命令就在后端容器里执行，能上网（D20）。它这么说，是因为底层框架 deepagents 给“执行命令”工具自带的说明写的是“在隔离的沙箱里执行”；镜像里又没有 `git`、`curl`、`wget`。
- 另外两条是当时有意的设计：技能只能在技能页增删；10 月 26 日去掉了 `pip`（需求池 R15 标为不做）；10 月 23 日给命令加了写入限制，只能写本会话目录。

用户提出三点：优化提示词和工具说明；镜像带上 `git`、`wget`、`curl` 等基础工具；允许在对话里安装技能，并且“允许做任何事，除非是修改自身代码”。

## 备选方案（放开到哪一步）

1. 只做对话里装技能和基础工具，不放开装包，写入范围不变。
2. 再允许装 Python 包（装到单独目录），写入范围不变。
3. 再允许写 `.workdata` 里的其他个人数据，配置文件仍然改不了。
4. 全部放开，只保护程序代码。

## 结论

采用方案 4（用户 2026-11-19 选定）；对话里装技能的审批跟随会话权限（用户选定）。

- **写入范围：只保护代码。** 命令照旧用普通用户（uid 1000）执行，程序代码和后端自己的 Python 环境属于 root，改不动。写入限制（Landlock）从“只能写本会话目录”改成“能写整个数据目录 `.workdata`、`/tmp`、`/dev`”，代码所在的目录不在放行范围里，等于保护代码有两层。读一直不受限。
- **能装包。** `pip` 作为项目依赖锁定版本（26.3）。命令里的 `pip install` 装到 `.workdata/cache/exec-packages/`（`PIP_PREFIX`，配 `PIP_IGNORE_INSTALLED=1`），只有执行的命令找得到（`PYTHONPATH`），后端进程不受影响；所有会话共用，重建镜像后还在；装坏了删掉这个目录就恢复。不用 `--target` 的装法：它遇到目录里已有的同名文件夹就整个跳过，后装的包会装不全（审查时用两个包实测过）。网络慢时在 `.env` 里设 `PIP_INDEX_URL` 换镜像站（会被命令看到，别写带账号密码的地址）。取代“去掉 pip”的决定（修订 D20、R15）。
- **基础工具。** 镜像里加 `git`、`curl`、`wget`、`unzip`、`zip`、`jq` 和 CA 证书。硬底线里本来就有“下载后直接执行（`curl … | sh`）”，任何档位都先问。
- **对话里装技能。** 新工具 `install_skill`：智能体先把技能下载到会话目录、打成 `.zip`（或给单个 `SKILL.md`），工具读出来后走和技能页上传完全相同的检查与落盘（检查逻辑从后端挪到智能体一层共用）。不把 `/skills/` 改成可写：直接写进去会绕过检查。子智能体没有这个工具。
- **装技能的审批跟着执行命令走。** “每次先问”“只问执行命令”两档都先问，规则文件放宽不了；“跳过所有审批”时直接装。
- **提示词与工具说明。** “执行命令”的说明换成与实际一致的（和智能体同一个环境、能联网、有哪些工具、能装包、装不了系统软件、改不了自身代码、先试再下结论）；系统提示词写明同样的事实和装技能的步骤。
- **仍然有的限制：**
  - 没有 root，装不了系统软件（`apt`）：让命令用 root 就保护不了代码了，要加系统软件只能改镜像。
  - 硬底线照旧（D25），并加一条“删除或改写本会话目录之外的数据”：命令的当前目录是 `/workspace/<会话>/`，模型写出来的多半是 `../别的会话`、`../../config` 这类，不带 `.workdata` 几个字，原来的规则认不出。现在跟着 `cd` 按路径的写法推，删改的目标出了本会话目录就算，任何档位都先问。只看文字、不看磁盘：写明 `/workspace/<某个会话>/` 的绝对路径当作本会话；用 Python 脚本、变量拼出来的路径认不出。
  - 文件工具里 `/skills/` 仍是只读，装技能走 `install_skill`。

## 原因与代价

- 智能体能自己完成“下载、解包、装依赖、装技能”这类事，不用用户到页面上代劳。
- 代价：**命令能改 `.workdata` 里的配置**，包括审批规则和 MCP 服务清单，等于能改自己的权限；还能改别的会话的文件、技能目录、知识库原文件、向量模型文件（模型文件启动时按哈希校验，坏了会重新下载）。备份改不了：后端容器里看不到备份目录。把关的只剩两样：会话的审批权限，和硬底线对这类命令的文字判断（挡的是模型一时糊涂，不是恶意，见 D25）。
- 代价：**“代码改不了”只对直接写成立。** 程序代码和后端的 Python 环境属于 root，命令（uid 1000）写不动，Landlock 也不放行，这是两层。但命令能改 MCP 服务清单和 npx 的包缓存，而本地 MCP 服务是后端以 root 启动的：在 Mac 的 podman 上（共享目录不区分用户）这是一条间接的路。命令也能直接往技能目录里放文件，绕过 `install_skill` 的检查。这些是“全部放开”自带的后果，不为此改 MCP 的运行方式。
- 代价：**不在容器里跑后端时没有代码保护。** 后端不是 root（比如在宿主机上直接跑）时，命令和后端是同一个用户，不换用户也不加 Landlock，代码改得动。正式的运行方式是容器（D27），这种情况只出现在开发调试时。
- 代价：**技能是给智能体的长期指令。** 装上后对以后所有会话生效；会话选了“跳过所有审批”时，网页、文档里的话有可能诱导它装上别人的技能。提示词要求只装用户在对话里明确要装的，但这只是约束模型，不是强制。技能页上随时能停用、删除。
- 代价：装的包对所有会话生效，同名的包会盖住后端环境里的版本（只对命令而言）；`pip` 用这种装法时不看后端环境里已有的包，依赖会再下载一份。
- 代价：镜像多约 100 MB。
- 代价：会话之间、命令与配置之间的隔离比第二轮优化时弱了；要收回去，把 `local_sandbox.py` 里放行的目录改回会话目录即可。
