# 个人智能体：功能梳理与优化建议

日期：2026-10-19　范围：当前已实现的全部功能（不含需求池里尚未开工的扩展项）　
方法：分五块（对话与运行、工作区与文件、知识库、外部集成与管理页面、平台运维与用量）逐一对照文档与代码核实，再合并去重。文中的"文件:行号"都核对过；标"推测"的是没能实测、只从代码推断的。

---

## 0. 一页结论

**整体判断**：主链路完整、可靠——对话、停止与续传、审批、文件、记忆与文档检索、三个管理页面、备份恢复都能跑通，单元测试与端到端测试全绿。问题集中在五类，而不是"功能缺失"：

1. **状态没存下来、前后不一致**：会话里换的模型不保存；失败时已输出的内容模型不知道；被停止的命令生成的文件永远看不到。
2. **"每次先问"是唯一的防线，但有缺口**：被同意的命令能改审批规则文件、能调后端接口、能直连数据库、能删备份（D20 / D21 接受过一部分，但叠加起来比当时估计的大）。
3. **检索质量**：关键词检索把"的""我"也当关键词；相关度再低也凑满条数；模型不知道知识库里有哪些文档。
4. **运维命令与文档对不上**：改了 `.env` 后 `make restart` 不生效；日常用的是"开发模式"的容器；不少文档还停留在早期设计（沙箱容器、2 美元预算等）。
5. **体验细节**：执行命令的审批卡片看不清要跑的代码；看不出哪个会话在等审批；自动整理记忆用户看不见、也撤销不了。

**从架构看**（第 6 节）：模块之间的依赖方向是对的、每张表只归一个模块写，这两点守住了；上面五类问题大多能追到六个结构上的根因——智能体内核一个类管得太多、"会话设置"没有主人、"用户配置"散在三层、集成变更是全量重连加全局指纹、安全边界没有统一的信任模型、用量口径没有收口。第 6 节把第 4 节的建议按根因重新排成了八步路线，每一步都同时交付用户能感觉到的改进。

**需要你先拍板的几件事**见第 5 节；**立刻可修、代价很小的**见第 4 节的 P0。

**有一条是 2026-10-18 的改动引入的回归**：技能目录改成 `/skills/builtin/` 后，数据分析员定义里写死的 `/skills/excel/SKILL.md` 失效了，而且自定义子智能体本来就拿不到技能清单（`agents/main_agent/runtime/agent.py:593-604`，对比通用子智能体 `:571-581`）。每次数据分析第一步读技能都会失败。

## 1. 现状梳理：各功能怎么实现、有哪些规则

### 1.1 对话与运行

| 功能 | 用户看到的 | 背后怎么走 |
|---|---|---|
| 会话 | 新建、重命名（1～100 字）、拖拽排序、删除（有进行中或等待审批的运行时删不掉） | 点"新建"立即建一条（`ThreadList.tsx:50-56` → `threads/repo.py:23-34`）；删除连对话存档、工作区目录一起删（`agent.py:193-196`） |
| 标题 | 先显示首条消息前 30 字，第一次结束后变成 15 字以内的标题 | 后台用本次运行的模型生成（`followups.py:47-78`）；前端在 2/5/10/20 秒各刷新一次（`titleRefresh.ts:5`） |
| 一次运行 | 回答逐字出现，工具卡片、思考过程、子智能体卡片、待办清单 | 智能体的输出翻译成自定义事件（`agent.py:342-422`），加序号推给内存事件总线，每 200 毫秒批量写进 `run_events` 表（`manager.py:231-253`） |
| 实时推送与续传 | 刷新或断网后接着出 | SSE（服务器往浏览器单向推送的长连接）；重连时带上最后的序号；结束后内存只留 60 秒，之后查数据库（`event_bus.py:28`、`manager.py:164-184`） |
| 停止与"继续" | 点停止，下一句说"继续"接着做 | 已输出部分加一段中断说明写进对话存档（`agent.py:392-397`、`472-487`） |
| 审批 | 卡片上同意 / 修改后执行 / 拒绝 / 回复一句话 | 标成"先问"的工具触发暂停，运行记为"等待审批"；恢复前核对工具与规则的"指纹"（`agent.py:246-270`）；"回复"其实是带一句话的拒绝 |
| 预算刹车 | 一次运行到 100 次模型调用暂停，"继续"再给 100 次 | 每次调用结束计一次（`tracker.py:171-182`），调用前检查（`budget.py:56-64`） |
| 模型卡住 | 120 秒没新内容就停下，说明原因 | `litellm_proxy.py:183-193`；已输出部分保留 |
| 换模型 | 顶栏下拉框 | **只是页面临时状态**，随下一条消息发出（`ChatView.tsx:43`、`manager.py:73`） |
| 用量展示 | 每轮下方本轮用量，顶栏会话累计，都只显示 token | `adapter.ts:221-235`、`ThreadUsageBadge.tsx` |
| 回答渲染 | Markdown、代码高亮、复制、数学公式 | D19；`parts.tsx:93-106` |

关键规则：消息 1～100000 字；每条最多 10 个附件；同一会话同时只能有 1 个运行；工具结果在界面上只显示前 2000 字；服务重启时排队和运行中的记为失败，等待审批的不受影响（`runs/repo.py:187-194`）。

### 1.2 工作区、执行命令与文件

| 功能 | 用户看到的 | 背后怎么走 |
|---|---|---|

| 路径分流 | 智能体看到 `/workspace/…`、`/skills/builtin/`、`/skills/user/`、`/.agent/` | `runtime/files.py:34-48`；`/shared` 没挂进文件工具，只有 MCP 的 files 服务能读写 |

| 产物 | 回答里的文件卡片、右侧文件面板 | `write_file`/`edit_file`/`execute` 后对比 `outputs/` 前后（`agent.py:606-632`）→ `file.created` → 后台登记 |

| 加入知识库 | 文件面板一键加入 | `router.py:153-174`，整份复制进知识库 |

关键规则：命令默认 120 秒、最长 600 秒（越界是在用户同意之后才拒绝，`local_sandbox.py:72-76`）；输出超过 30000 字符写日志、日志最多 20MB（写死在代码里）；脱离进程组的后台进程最多再等 2 秒，之后不管。

### 1.3 知识库（记忆 + 文档）

| 功能 | 用户看到的 | 背后怎么走 |
|---|---|---|
| 记住 | 说"记住……"，对话里显示"已记住" | `remember` 工具当场向量化（把文字转成一串数字，意思相近的数字也相近）与 jieba 分词，写入 `knowledge_items`（`runtime/knowledge.py:37-66`） |
| 会后自动整理 | **界面上没有任何提示** | 每次顺利结束后，用会话所选模型读本轮问答，对照最多 10 条相近记忆，回 JSON 新增 / 更新 / 删除（`extraction.py:86-99`、`160-195`） |
| 常驻与召回 | 设为常驻的每次都带上；相关记忆自动带上 | 常驻全部带上；相关记忆最多 5 条、相似度下限 0.3、最多等 5 秒（`config/settings.py:49-53`），拼到系统提示词末尾（`runtime/knowledge.py:124-174`） |
| 知识库页 | 记忆 / 常驻 / 文档三个视图，搜索、增删改、设常驻 | 不搜索按时间倒序；搜索走混合检索（`backend/api/knowledge.py:86-93`）；每页 50、最多 200 条 |
| 文档 | 上传 10 种格式（≤50MB），处理完回答带出处 | markitdown 转 Markdown → 切块（约 600 token、重叠 80）→ 每批 2 段向量化（`library.py:109-160`）；失败不自动重试 |
| 检索 | 回答里的出处链接，点开看原文段落 | 向量与关键词两路各取 top_k×4，再用"倒数排名融合"合并（`pgvector.py:249-289`） |

关键规则：`search_knowledge` 默认 5 条、最多 20；`read_document` 前后各 2 段；条目 1～2 万字；常驻建议上限 2000 token（超了只提示）；自动整理消息与回答各取前 4000 字，出错重试 3 次。

## 2. 冲突点（功能之间、规则之间、文档与代码之间）

按对使用的影响排序。

1. **"按会话换模型"名不副实**（对话 + 模型页）
   - 选择只存在页面里，切页、刷新、换会话后悄悄回到建会话时的模型（`ChatView.tsx:43`）；后端从不回写 `threads.model`（`backend/runs/manager.py:73`，唯一的 `UPDATE threads SET model` 在删模型时）。
   - 连带：模型页"N 个会话在用"、删模型时改派哪些会话，都按建会话时的旧值算。

2. **"每次先问"是唯一防线，但一条被同意的命令能让它失效**（工作区 + 集成 + 平台）
   - 能改 `workdata/config/` 里的审批规则、MCP 清单、技能（D21 第 7 条已接受，`execute` 写死先问只堵住了一处）。
   - 能往 MCP 清单加一个本地服务、或改 `workdata/cache/npm` 里的服务代码——MCP 进程以 **root** 运行（实测 uid 0），下次重连就以 root 身份执行（推测）。
   - 没设访问令牌时能直接调后端接口，包括提交审批决定的 `/runs/{id}/resume`；配合杀不掉的后台进程，理论上能自动替你同意以后的审批（推测，未实测）。
   - 能用默认账号密码 agent/agent 直连数据库，读写全部对话与记忆；能删掉 `workdata/backups/`（备份是最后一道防线）。
   - D20 第 22 行"一条被同意的命令改不了代码和审批规则"在 D21 之后已经不成立。

3. **"看清命令再同意"做不到**（工作区 + 对话）
   - 使用指南要求看清命令（`usage.md:54`），提示词却要求模型先把步骤写进脚本再执行（`system.md:10`、`data_analyst.md:11`）。审批卡片只显示一个 JSON（多行脚本满屏 `\n` 和 `\"`，`approval.tsx:169-175`），看不到脚本内容，也没有接口能读未登记的脚本。

4. **页面改规则会打断等待中的审批**（MCP 页 + 审批）
   - 审批"指纹"覆盖全部工具（`agent.py:272-276`）：在 MCP 页把任何一个工具改成"自动"，所有会话里等待中的审批都作废——正好打断"这个工具以后别问了"这个最自然的操作。
   - 通配规则还会让页面开关失灵：使用指南建议写 `<服务名>_*: ask`，之后在页面上点"自动"，新规则排在通配后面，永远轮不到（实测仍是"先问"）。

5. **用户配置写坏时的兜底与文档不符**
   - D21 与 `usage.md` 说"先用 `config/` 的设置"，但 MCP 那边实际是整体变成空配置（`backend/settings/service.py:70-73`），连自带的 files 服务也没了，页面显示"还没有 MCP 服务"。

6. **两条记忆写入路径重叠，自动整理与"完全可控"冲突**（知识库）
   - 提示词让模型对长期信息主动 `remember`（`system.md:17`），会后自动整理做同一件事；`remember` 写入前不查重，两条路的来源都显示"对话中记下"。
   - 自动整理能改、能删任何非常驻记忆，**包括你手动加的**；改完来源和创建时间不变，没有记录、没有通知、不能撤销。

7. **记忆与文档共用一张表的副作用**（知识库）
   - 文档片段没有标签，模型检索时带了标签，文档就全被筛掉。
   - 接口仍允许修改、设常驻、单删文档片段；被设成常驻的片段会进每次的系统提示词。
   - 重新处理文档会生成新的片段编号，历史回答里的出处全部显示"已不在知识库里"。

8. **用量口径不一致**（用量 + 模型页）
   - "输入 token"本身已含缓存命中部分（`runtime/tracker.py:199-201`），用量页又把"缓存读"并列一栏，长对话的输入看起来虚高好几倍。
   - 顶栏累计含标题生成、记忆整理、向量化（它们在后台稍后写入），所以各轮相加不等于顶栏，顶栏还会过几秒自己变。
   - "只显示 token"，但后台照记费用，模型页又说价格"只做记录，不参与统计"——实际 `llm_usage.cost` 就是按它算的；模型页的"测试"不记入用量。

9. **改了 `.env` 后的生效命令不对**（平台 + MCP + 模型）
   - `make restart` / `make restart-gateway` 用的是 `compose restart`（`Makefile:88、98`），不会重读 `.env`；而 MCP 安装对话框、后端提示都写"重启后端"。要 `make up`（重建容器）才生效，`usage.md` 前后说法也不一致。

10. **"日常运行"其实是开发模式**（平台）
    - 日常用的容器挂着你电脑上的源码、开着自动重载，镜像里打包的代码从没被用上（`backend.Dockerfile:56` 被 compose 覆盖）。`make restart` 后接口是新的，8000 的界面还是旧的。

11. **设置页与三个管理页重复、文字过时**（管理页面）
    - 设置页仍写"在 config/ 里改""在 agents/skills/ 下加文件夹"（`SettingsPage.tsx:17、60-62、264-266`）；两个"重新加载"做同一件事；同一状态叫"未启用"和"已停用"两种名字；明暗切换出现两处。

12. **失败时已输出的部分模型不知道**（对话，违背 D07）
    - 停止和卡住会把已输出部分写进对话存档，失败不会（`agent.py:392-407` 对比 `408-412`）；补上的中断说明还写着"用户停止或服务中断"。

13. **大小上限对不上**：上传 100MB，知识库 50MB，"加入知识库"按钮只看后缀，超过 50MB 的要整份复制完才报错。

14. **三套会话编号**：地址栏是完整 UUID，用量页显示前 8 位，工作目录是 `c_xxxxxxxx`（界面上从不显示，但使用指南让你去 `workdata/workspace/<会话>/` 找文件）。

15. **删除会话的确认文字不完整**：只说"对话内容将全部删除"，实际文件也一起删；而记忆、用量、加入知识库的文档都保留。

16. **文档与代码不符（成片过时）**
    - 设计文档：§3 / §5 / §9 还是沙箱容器；§7.5 "执行代码默认自动"；§8 的召回阈值 0.75、提取用便宜模型、"重建向量脚本"；§10.1 的"排队"状态；§10.7 网关重试与备用模型；§10.8 "2 美元上限"；§13.3 的右栏四个标签与会话搜索。
    - README 第 3 行"隔离环境里执行代码"；D03 说 reload 未实现；D20:13 "改 `WORKDATA_DIR` 就能换位置"（compose 写死了）；管理页面设计稿的"安装将覆盖""密钥写进 .env"已被 D21 推翻；`architecture.md:177` 仍写 `/skills/`；成功标准核对里"费用都能统计到"已不成立。

## 3. 未完成点（用户实际会碰到的）

**对话**
- 失败后没有"重试"（设计 10.7）；会话没有搜索（13.3）；归档做了一半（表里有 `archived` 字段，没有接口能设置）。
- 停止或失败后，待办卡片里正在做的那一项一直转圈（`parts.tsx:243-247`）。
- 订阅推送没处理出错：遇到 401 之类会永久断开，界面却一直显示"运行中"（`events.ts:12-18`）。
- 需求池里会碰到的：拒绝后卡片显示"出错"和英文结果（R23）；标题超过 20 秒才生成就不刷新（R18）；正文里的 `\[1\]`、`$HOME` 被当成公式（R25）。

**工作区与文件**
- **被停止的命令生成的产物永远看不到**：下次运行一开始就把它们当"已有"（`agent.py:363`），既没卡片也不进面板。
- 文件面板只显示 uploads/ 与 outputs/（脚本、日志看不到）；不能删单个文件；运行结束不刷新列表；"已加入知识库"不保存，同一文件能反复加入。
- 智能体生成的网页或 Markdown 报告里，相对路径的图片在预览里是坏图（推测，代码推断）。
- 时区没设（命令里的"今天"很可能是 UTC，推测）；没有 xlrd，老格式 `.xls` 读不了，智能体又不能装包。

**知识库**
- 换向量模型会悄悄出错：检索不按条目的向量模型过滤，也没有重建脚本（R31）。
- 没有"忘掉 / 更正"：只能再记一条新的，或自己去知识库页删。
- PDF 实际不按标题切块（markitdown 转出的 PDF 没有标题），跨页句子被切断；表格第 2 块起没有表头；同一文件能重复加入；超过 50MB 要传完才拒绝。
- 子智能体看不到常驻信息（"回答简洁点"这类偏好不会传给数据分析员）。
- 使用指南没写怎么关自动整理（`knowledge.auto_extract`），也没写它会改删已有记忆、每轮多一次模型调用。

**模型与集成**
- 自带的 gemini、gpt 没写上下文长度、能否看图、价格（`config/models.yaml:26-42`）：发给它们的图片会被换成"[图片已省略]"（`cleanup.py:70-71`），推测这两个模型其实能看图。
- 设计 7.1 和先行验证 V2 要求给 Claude 配提示缓存（`cache_control_injection_points`），没配，需求池也没登记。
- 新增模型只有保存后才能测试；"自动查询"没做；子智能体的"可用工具"字段没做，界面上也看不到有哪些子智能体。
- 模型来源能在 `config/app.yaml` 的 `models.sources` 里加，文档没提；"本机 Ollama"来源只能加向量模型，而向量模型又只读，加了也用不上。

**平台**
- 容器没有重启策略、没有内存上限；开机后要先 `podman machine start` 再 `make up`。
- `/api/health` 只返回 ok，看不到数据库、网关、Ollama 是否正常。
- 测试库用完不关（实测已连续运行 2 天，一直占虚拟机内存）；网关日志没设保留期，会一直变大并进每份备份。
- 重启、构建、恢复会打断进行中的运行，文档没说；数据库迁移前不自动备份；手机打开时侧栏挤压（推测）。

## 4. 优化建议

每条：场景 → 建议 → 代价。优先级按"对日常使用的影响 ÷ 代价"排。

### P0：立刻修（属于缺陷或回归，代价小）

1. **数据分析员读不到技能（回归）**
   - 场景：每次数据分析第一步读技能就失败，上传的技能它也用不上。
   - 建议：自定义子智能体像通用子智能体一样传入技能来源；`data_analyst.md` 去掉写死的路径；补测试。
   - 代价：很小。
2. **会话里换的模型存下来，并在每轮页脚显示模型名**
   - 场景：昨天切到 gemini，今天打开又变回 claude，没注意就用错了模型。
   - 建议：发起运行时回写 `threads.model`；页脚直接显示本轮模型。
   - 代价：极小；"N 个会话在用"也会变准。
3. **补齐自带模型的信息**
   - 场景：给 gemini 发截图，它说看不到。
   - 建议：在 `config/models.yaml` 补上下文长度、看图能力、价格，然后 `make restart-gateway`。
   - 代价：要按厂商资料逐个核对。
4. **改了 `.env` 后的生效命令统一并改对**
   - 场景：填了密钥，按提示重启后照样"缺少环境变量"。
   - 建议：`make restart` / `restart-gateway` 改成重建容器（`up -d --force-recreate --wait <服务>`）；界面和文档统一写这条命令。
   - 代价：多几秒，同样会打断进行中的运行。
5. **MCP 用户文件写坏时退回 `config/` 的设置**（与 D21、使用指南对齐）
   - 代价：小。
6. **运行失败：中文原因、已输出部分写进对话存档、错误条上加"重试"**
   - 代价：报错对照表要维护；重试后会出现两条相同的用户消息。
7. **被停止的命令生成的文件找回来**：打开文件面板或运行开始时，把 outputs/ 与登记表对一遍。
   - 代价：小。

### P1：安全与可信（涉及 D20 / D21 的取舍，需要你拍板）

8. **让"每次先问"名副其实**，按收益从高到低：
   - 备份目录移出 `workdata/`（不挂进容器），备份清单里记下 `LITELLM_SALT_KEY` 的指纹，恢复时核对；
   - 首次 `make` 时自动生成访问令牌和数据库密码写进 `.env`（命令读不到 `.env` 和后端环境变量），5432 不对宿主机开放；
   - npm 缓存移出 `workdata/`，MCP 进程降到 uid 1000，目录里的 MCP 包写精确版本；
   - 每条命令结束、且没有别的命令在跑时，清掉 uid 1000 的残留后台进程。
   - 代价：第一次要输一次令牌（Cookie 有效一年）；已有数据库要改一次密码；调试数据库要 `compose exec` 进去；`workdata/config` 的写保护仍要等 R33。
9. **"日常运行"和"开发运行"分开**
   - 好处：8000 的界面和接口永远同一版本；正在改的代码不影响正在用的助理；就是"独立容器"的雏形。
   - 代价：改 Python 也要 `make build`，失去"几秒生效"。

### P2：日常体验（高频，值得做）

10. **执行命令专用的审批卡片**：命令按多行代码显示；显示时限与工作目录；命令里引用的会话内脚本直接展开内容；时限越界在审批前就拦下。
    - 代价：前端改动加一个读会话文件的接口（见第 16 条）；长脚本要折叠。
11. **看得出哪个会话在跑、在等审批**：会话列表显示"运行中 / 待审批"小点；浏览器标签页标题加"待审批 / 完成"前缀。
    - 代价：会话列表接口多带一个字段（一条 SQL）。浏览器通知要授权，可以后做。
12. **检索质量三件事**
    - 关键词检索加中文停用词、丢掉单个汉字；
    - 结果加相关度门槛，低于下限且关键词也没命中的丢掉，"没找到"才有意义；
    - 系统提示词附上文档标题清单（最多 30 个），并写明"问题可能涉及这些文档时先检索"。
    - 代价：门槛要用真实数据调，调高了会漏；提示词每次多几十到几百 token。
13. **自动整理记忆：看得见、能撤销、不碰手动条目**
    - 自动整理只动它自己写的、不改你手动加的；单独的来源值，界面能区分；知识库页加"最近自动整理"（显示更新时间、来源会话、撤销）。
    - `remember` 写入前查重，很相近时改为更新；"已记住"提示上加"撤销 / 取消常驻"按钮（事件里已带条目编号，改动很小）。
    - 代价：一次数据库迁移、一张记录表、一个视图。
14. **审批卡片加"以后自动执行"**（`execute` 除外），同时"指纹"只比对这次涉及的工具；页面写的按工具规则排在通配前面。
    - 代价：要修订 D18 第 4 条；放宽的范围变大。
15. **会话与输入体验**
    - 对话页空状态直接放输入框，第一次发送或上传时才建会话（减少一串空的"新会话"）；
    - 草稿和待发附件按会话保存（现在切换会话就丢）；支持粘贴截图；超过 5MB 的图片在服务端缩小再发（用已装的 Pillow）；
    - 会话标题过滤（纯前端），把归档补完（比删除安全）。
    - 代价：都小；上传需要会话编号，所以第一次上传时就要建会话。
16. **文件面板与磁盘同步**：新增按路径读会话文件的接口（复用现有越界检查与安全响应头）；面板加"全部文件"一栏；单个文件可删除（要确认）；记住"已在知识库"。
    - 代价：中等；要过滤掉 `__pycache__` 一类杂文件。
17. **用量口径修正**："新输入"（输入减缓存读）和"缓存读"分开，趋势图按新输入加输出；可选一个默认关闭的"按价格折算"开关（后台已有费用数据，是否触碰"只显示 token"的决定需要你确认）。
18. **设置页瘦身**：只保留规则清单、全部工具生效表、预算，加一块"系统状态"（数据库、网关、Ollama、MCP 是否正常，上次备份几天前，令牌与局域网是否开启）；"重新加载"只留一处并写清用途。
19. **需要密钥的 MCP 服务从三步变一步**：先把文字统一成 `make up`；再给后端加一个可选的密钥文件（如 `.env.mcp`），R32 落地后可去掉。
    - 代价：多一份密钥文件；Podman 对可选 env_file 的支持要先验证。

### P3：低成本清理

20. **文档一次性修订**：第 2 节第 16 条列的全部过时内容；使用指南补上关闭自动整理、面板显示范围、各项预览上限、重启会打断对话。

## 6. 架构层面：耦合、内聚与用户体验

先说清两个词：**耦合**是两块功能互相牵扯的程度——改一块要不要跟着改另一块；**内聚**是一块内部的东西是不是都为同一件事服务。目标是"块与块之间松、块内部紧"，这样改一处不会意外坏另一处（用户感到的就是"更稳、行为一致"）。

### 6.1 现状地图（实测）

**依赖方向**：`backend → agents → config → common` 单向，由 import-linter 自动检查，没有违反。各块代码量（不含测试）：

| 块 | 行数 | 职责 | 拥有的数据（只有它写） |
|---|---|---|---|
| agents.runtime（智能体内核） | 2597 | 组装智能体、驱动运行与审批、事件翻译、技能目录、知识注入、预算、标题 | 对话存档（LangGraph 自己的表） |
| agents.knowledge（知识库） | 1467 | 记忆与文档的存取、切块、检索、自动整理 | `knowledge_items`、`knowledge_documents` |
| agents.models（模型网关） | 711 | 调网关、模型信息、增删改测、卡住超时 | 网关数据库里的模型 |
| agents.workspace（工作区） | 678 | 会话目录、执行命令、产物登记 | `workspace_files` |
| agents.integrations（集成） | 341 | MCP 客户端、审批判定 | — |
| agents.usage（用量） | 255 | 每次模型调用的记录与汇总 | `llm_usage` |
| backend.runs（运行编排） | 872 | 发起、续传、取消、恢复、后续任务 | `runs`、`run_events` |
| backend.settings / backend.models | 517 / 221 | 管理页面的修改 | `workdata/config/` 里的文件 |
| backend.threads | 165 | 会话 | `threads` |
| backend.runtime | 331 | 事件总线、任务队列、运行控制 | `jobs` |
| config | 589 | 配置加载与合并 | — |

**做得好的**（要保住）：
- 依赖单向且有自动检查；外部依赖都在可替换接口后面，有契约测试（D05）。
- **每张表只被一个模块写**（实测：`threads` 只在 `backend/threads/repo.py`，`llm_usage` 只在 `agents/main_agent/usage/repo.py`……）——数据归属清楚。
- 前后端的事件协议只有一份定义（`runtime/events.py`），前端类型由它生成，`make check` 核对是否一致。
- 管理页面的修改走同一个流程："先检查 → 内存里改 → 校验 → 原子写入 → 生效"。

### 6.2 六个结构上的根因

#### 根因一：智能体内核一个类管得太多（内聚低）

- **现象**：`MainAgent`（`agents/main_agent/runtime/agent.py`，632 行）有约 25 个方法，横跨：运行与恢复（`run`、`resume`、`check_answers`、`_drive_events`）、集成（`reload_integrations`、`update_rules`、`probe_mcp`、`tool_approvals`）、技能、会话删除、记忆整理（`extract_memories`）、标题（`generate_title`）、知识注入、组装主智能体与子智能体。
- **组装逻辑有两份**：通用子智能体（`_general_purpose`，:571-581）和自定义子智能体（`_subagent`，:593-604）各写各的，一个拿到了技能来源、一个没有；子智能体也都拿不到常驻信息（知识上下文只给主智能体）。
- **用户感到的**：数据分析员读不到技能（10-18 的回归就是这样漏掉的）；"回答简洁点"这类偏好不传给子智能体——**主智能体和子智能体行为不一致**。
- **建议**：`MainAgent` 保持为对外的薄门面（设计 §6.4 的"总入口"不变），内部拆成：
  - **能力组装器**：从一份"这次运行能用什么"（工具、技能来源、知识上下文、审批中断点、中间件）同时生成主智能体和每个子智能体，子智能体只声明"在此基础上去掉 / 加上什么"；
  - **运行驱动**：`run` / `resume` / 审批核对 / 事件翻译；
  - 记忆整理、标题生成挪回各自的模块（`knowledge.extraction`、`titles`），门面只转一下。
- **代价**：中等的重构，行为不变，靠现有测试兜底；要先补"主智能体与子智能体能力一致"的测试。

#### 根因二："会话设置"没有主人（职责错位）

- **现象**：会话用哪个模型，前端组件里临时持有（`ChatView.tsx:43`），后端只在建会话和删模型改派时写 `threads.model`；归档字段有、没入口；草稿和待发附件在组件里，切换就丢。
- **用户感到的**：换的模型刷新就丢、"N 个会话在用"不准、删模型后开着的会话仍用旧模型（10-18 审查第 7 条只补了前端同步，根子没动）。
- **建议**：明确 **会话（threads）是"会话设置"的唯一主人**：模型、归档、（可选）草稿都存在会话上；运行只引用会话当时的设置；前端只显示和修改会话，不另存一份。
- **代价**：小；`PATCH /threads/{id}` 加字段，前端把本地状态换成读会话。

#### 根因三："用户配置"散在三层，各自兜底（耦合 + 内聚都差）

- **现象**：
  - 读：`config/integrations.py`（MCP、规则）、`config/settings.py`（自己写了一套读 `app.yaml`）、`agents/runtime/skills.py`（读 `skills.yaml`）；
  - 写：`backend/settings/store.py`（`UserConfigFiles`），`backend/models` 借用它，`agents/runtime/skills.py` 又自己写了一份原子写入；
  - 兜底各不相同：MCP 文件写坏 → 整体变空（连自带服务也没了）；`app.yaml` 写坏 → 忽略；`skills.yaml` 写坏 → 当作没停用。
- **用户感到的**：同样是"手改写错了"，三个页面的反应不一样，有的还与文档说法相反。
- **建议**：抽出一个 **用户配置仓**（放在 config 层，agents 与 backend 都只通过它读写 `workdata/config/`）：
  - 读：统一返回"采用的内容 + 给用户看的原因"；
  - 写：统一原子写入、写前校验、不覆盖写坏的文件；
  - 兜底统一为"**坏了就用 config/ 的基础配置，页面上提示哪个文件出了什么错**"；
  - 各页面只调用它，设置页的"系统状态"直接列出所有文件的状态。
- **代价**：中等；它也是根因五（安全收口）的前提——可写配置的位置集中到一处，才好统一保护。

#### 根因四：集成变更是"全量重连 + 全局指纹"（块内耦合过紧）

- **现象**：改任何一个 MCP 服务 → 全部服务重连（`mcp_adapters.py:36-39`）；审批"指纹"覆盖全部工具（`agent.py:272-276`）；有任何对话在跑，就不许改任何服务。
- **用户感到的**：
  - 在 MCP 页把一个工具改成"自动"，所有会话里等待中的审批都作废；
  - 长任务跑着时，想停用一个无关的服务被拒；
  - 停用一个服务，files 服务也跟着重启。
- **建议**：按服务粒度：
  - MCP 客户端支持单个服务的加、删、重连；
  - 指纹只算"这次暂停涉及的工具"；
  - "有对话在跑就拒绝"缩到"这个服务正被运行使用"。
- **代价**：中等；要处理好组装缓存与指纹的一致性。是"审批卡片加'以后自动执行'"（P2 第 14 条）的前提。

#### 根因五：安全边界没有统一的信任模型（横切关注点无主）

- **现象**：
  - 审批在 `agents.integrations`，执行隔离在 `agents.workspace`，网页防护在 `backend.security`，可写目录与数据库凭据在 `docker-compose.yml`，MCP 进程身份在 `mcp_adapters`；
  - D20、D21 各自接受了一些代价，**叠加起来出现缺口**：被同意的命令能调后端接口（含提交审批）、能直连数据库、能删备份、能改以 root 运行的 MCP 代码（第 2 节第 2 条）。
- **用户感到的**："每次先问"给人的安全感比实际高。
- **建议**：先写一份 **信任边界决策（D22）**，再按它收口：
  - 三类主体：**你**（浏览器）、**模型与它执行的命令**、**外部 MCP 服务**；
  - 逐项写清各自能碰什么：后端接口、数据库、`workdata/` 的哪些子目录、网络；
  - 落地的就是 P1 第 8 条的那几项，外加 R33（命令只能写会话目录与缓存）。
- **代价**：决策本身不贵；落地要动 compose、Makefile、首次准备流程。需要你拍板（第 5 节第 1、7 条）。

#### 根因六：用量口径没有收口（反向依赖 + 三处各算各的）

- **现象**：
  - `agents.usage` 反过来依赖 `agents.runtime`（导入了 `UsageReported`、`UsageTotals` 这两个事件类型）；
  - 顶栏、每轮页脚、用量页三处各自组合数字："输入"已含缓存却与"缓存读"并列，顶栏含后台调用。
- **用户感到的**：几个地方的数字对不上、会自己变、输入虚高。
- **建议**：用量事件类型与"展示口径"（新输入 / 缓存读 / 输出、是否含后台调用）都收进用量模块，内核只负责发出；三处显示共用一个口径函数。
- **代价**：小。

### 6.3 前端

- **对话页是枢纽**：`features/chat` 引用了会话、用量、模型、知识库、文件五块——作为组合页面是合理的。
- **小的越界**：
  - `features/models` 借用 `features/usage` 的数字格式化；
  - 三处直接引用 `components/chat/format`（聊天组件的内部文件，R20 记过）。
  - 建议把格式化挪到共用的 `lib/format`。
- **页面状态与服务器状态混放**：会话的模型、草稿、待发附件都在组件的 `useState` 里（根因二的前端一面）。建议按会话存放的前端状态集中一处，服务器能存的（模型）就存服务器。
- **设置页与三个管理页重复**：设置页改为只做"审批与预算 + 系统状态"。

### 6.4 根因与症状的对应（修一次根因，消掉多个症状）

| 根因 | 第 2、3 节里由它引起的症状 | 第 4 节对应的建议 |
|---|---|---|
| 一、内核管得太多 | 数据分析员读不到技能；子智能体没有常驻信息；失败时已输出部分不进存档 | P0-1、P0-6、P3-26（子智能体常驻） |
| 二、会话设置没主人 | 换模型不保存；"N 个会话在用"不准；删模型后开着的会话仍用旧模型；归档没入口；草稿和附件切换就丢 | P0-2、P2-15 |
| 三、用户配置散在三层 | MCP 文件写坏连自带服务一起没；三处兜底不一致；设置页文字过时 | P0-5、P2-18 |
| 四、全量重连 + 全局指纹 | 改一个工具，等待中的审批全作废；通配规则让开关失灵；有对话在跑就不能改 | P2-14 |
| 五、没有信任模型 | 命令能调接口、能连数据库、能删备份、能改 root 运行的 MCP 代码 | P1-8 |
| 六、用量口径没收口 | 输入虚高；顶栏与各轮对不上；测试不记入 | P2-17 |

另外三件事不是某个根因的症状，而是平台决定，单独处理：**日常运行与开发运行分开**（P1-9）、**改 `.env` 后的生效命令**（P0-4）、**检索质量**（P2-12，属于知识库块内部）。

### 6.5 建议的推进路线

每一步都同时交付用户能感觉到的改进，而不是"先重构、很久以后才见效"。

| 步骤 | 做什么 | 用户马上感到的 | 规模 | 需要拍板 |
|---|---|---|---|---|
| 0 | 第 4 节 P0 全部（7 条） | 数据分析员能用技能；换模型不丢；gemini/gpt 能看图；改密钥按提示能生效；失败可重试 | 小 | 否 |
| 1 | 会话设置归位（根因二） | 模型、归档跟着会话走；草稿和附件不丢 | 小 | 否 |
| 2 | 用户配置仓（根因三） | 手改写错时所有页面反应一致、都能看到原因；设置页变成"系统状态" | 中 | 否 |
| 3 | 信任边界 D22 + 收口（根因五） | "每次先问"名副其实；备份不会被命令删掉 | 中 | **是** |
| 4 | 内核拆分 + 统一能力组装（根因一） | 主智能体与子智能体行为一致；以后加能力不再漏掉子智能体 | 中 | 否（行为不变） |
| 5 | 集成按服务粒度（根因四） | 改一个服务不打断别的；可以在审批卡片上"以后自动执行" | 中 | **是**（审批放宽） |
| 6 | 记忆写入统一（知识库块内） | 自动整理看得见、能撤销、不碰手动条目；检索结果更准 | 中 | **是**（自动整理默认开关） |
| 7 | 用量口径收口（根因六） | 各处数字一致、不再虚高 | 小 | 是否加"按价格折算" |
| 8 | 日常与开发运行分开 | 8000 永远是同一版本；就是"独立容器"的雏形 | 中 | **是** |

第 4 节的 P2、P3 里不属于这些步骤的体验项（如会话列表显示"待审批"、执行命令专用审批卡片、文件面板同步），可以穿插在任意两步之间做，彼此不依赖。
