## D15 细节：执行命令用的哪个 Python、pip 能不能装成

1. **用的 Python**：`/app/.venv/bin/python`，也就是后端自己的虚拟环境（`uv sync` 建的）。`local_sandbox.py:213-214` 把它所在目录放在 PATH 最前，后面才是 `/usr/local/bin:/usr/bin:/bin`；单元测试 `test_uses_the_same_python_as_the_agent` 钉着这一点。
2. **这个环境里没有 pip**：uv 建环境不带 pip，`uv.lock` 里也没有 pip，所以 `python -m pip …` 直接报"No module named pip"（本机按同一份锁文件建的 .venv 实测）。
3. **`pip` / `pip3` 命令**：虚拟环境里没有，于是落到 `/usr/local/bin/pip`，是基础镜像（`ghcr.io/astral-sh/uv:0.11.7-python3.12-trixie-slim`，基于官方 python:3.12-slim）自带的系统 Python 3.12 的 pip（推断，没进容器看）。
4. **以 uid 1000 运行 `pip install X`**：系统的包目录 `/usr/local/lib/python3.12/site-packages` 属于 root，写不了，pip 会自动改成"用户安装"，装到 `$HOME/.local/lib/python3.12/site-packages`；HOME 是 `.workdata/cache/exec-home`，正好在 Landlock 放行的目录里，命令又能上网（D20）→ 会显示"Successfully installed"（推断）。
5. **但用不到**：虚拟环境 `include-system-site-packages = false`，不看用户目录（本机 .venv 实测 `site.ENABLE_USER_SITE = False`），`import X` 照样失败。模型会以为装好了却用不了，可能反复重试（每次执行命令可能都要用户点同意）；装下的包还一直留在各会话共用的 exec-home 里。
6. **别的路**：`uv pip install --system` 或往 `/app/.venv` 装 → 没权限（属主 root，加上 Landlock）；在会话目录 `uv venv` 新建环境再装 → 装得上，但新环境里没有 pandas 等；`PYTHONPATH=~/.local/lib/python3.12/site-packages python …` 也能用上 pip 装的包——这两条只有很会绕的模型才想得到。
7. **建议**：提示词已写"不能安装新包"（`agents/prompts/system.md:10`、`agents/subagents/data_analyst.md`）。与之一致的最小改法是去掉系统 Python 的 pip（Dockerfile 一行，需要 `make build`）：`pip` 直接"command not found"，模型一次就明白。若反过来想让它能装（需求池 R15 待定），改法是 `_environment()` 加 `PYTHONPATH=<exec-home>/.local/lib/python3.12/site-packages`、改两处提示词——装的包会在所有会话间共用并一直留着，要你定。

## E16 专门评估：本地 MCP 服务改成普通用户运行

**现状**：本地（标准输入输出方式）MCP 服务是后端（root）用 mcp 库起的子进程（`mcp_adapters.py:326-338` → mcp 的 `stdio_client` → `anyio.open_process`，没有换用户的参数）。mcp 只给子进程 HOME、LOGNAME、PATH、SHELL、TERM、USER（`.venv/.../mcp/client/stdio/__init__.py:28-48`），加上配置里的 env 和 `npm_config_*`，并不直接继承后端的环境变量；但它是 root：能读 `/proc/<后端进程号>/environ`（`.env` 的全部密钥、LITELLM_MASTER_KEY、数据库地址），能改容器里的 `/app/.venv`（后端自己的 Python 环境，容器不重建就一直生效），能改 `.workdata/config`、`skills`（Landlock 只套在命令上）。

**为什么不用命令的 uid 1000，而是单独一个 uid（如 1001）**：同一个用户的进程能读彼此的 `/proc/<pid>/environ`（`reaper.py:19-21` 讲的就是这件事），也能结束、调试对方。MCP 服务若也是 1000，智能体执行的命令就能读到给 MCP 的密钥；两者若再共用缓存目录，命令还能往 npm 缓存里塞东西，由 MCP 服务去执行。换成 1001 后：命令（1000）读不到 MCP 的密钥，MCP 服务也读不到后端（root）的环境。

**要改的地方（第一步：换用户）**
1. `deploy/backend.Dockerfile:39` 旁边再建一个用户 uid 1001（只用来跑 MCP 服务，不建家目录、不能登录）。
2. `agents/main_agent/integrations/mcp_adapters.py` 的 `_connection()`：后端是 root 时，标准输入输出方式的命令改成 `setpriv --reuid=1001 --regid=1001 --clear-groups -- <原命令> <原参数>`；env 里设 HOME、USER、LOGNAME，`npm_config_cache` 指向新目录（原来的 `.workdata/cache/npm` 是 root 建的，1001 写不进去）。`probe()` 走同一个函数，自然一起换。
3. "找不到命令"的提示要改：套上 setpriv 后不会再抛 FileNotFoundError，只会变成"连接失败：Connection closed"，要在 `_attempt` 前用 `shutil.which(config.command)` 先查（否则契约测试 `test_broken_server_fails_with_reason` 在容器里以 root 跑会失败）。
4. 启动时建好 `.workdata/cache/mcp-home` 并交给 1001（chown；chown 不了时退回 0777，靠命令的 Landlock 挡住）。
5. `/shared`：files 服务要往里写。宿主机上的目录（默认 `.workdata/shared`，或 `.env` 的 SHARED_DIR）要让 1001 写得进去——Mac 上 podman 的共享目录、Linux 原生 Docker 的用户映射表现不同，要实测（R16 记过原生 Docker 上 root / 1000 的权限冲突）；`make up`、`make restart` 建目录时可能要放开权限。
6. 文档：D25 的"影响"、compose 里那段注释、使用指南的排错。

**缓存与家目录放哪**：HOME = `.workdata/cache/mcp-home`（在数据卷里，重建容器不用重新下载）；npx 的缓存 `npm_config_cache = .workdata/cache/mcp-home/.npm`；uvx（uv）的缓存与它下载的 Python 默认跟着 HOME 走（`~/.cache/uv`、`~/.local/share/uv`），也可以显式给 `UV_CACHE_DIR`。不要放进 exec-home（那是命令的 HOME，uid 1000 能写）。换完第一次启动会重新下载服务包（要能连 npm 源）。

**Landlock 要不要也套上**：建议套，但放到第二步。第一步换用户后，1001 仍能写所有放开权限（0777）的目录（各会话目录、exec-home、/tmp），能读 `.workdata` 里大部分文件，能用 compose 里的默认账号经网络连数据库。Landlock 能把它的写入限制在 mcp-home、/tmp、/dev 和这个服务要写的目录（files 服务就是 /shared）；可每个服务要写哪里不一样，得在 `mcp_servers.yaml` 给服务加一个"可写目录"字段（改配置格式与版本号、MCP 页表单），这是要设计的活。

**风险**：目录权限在 Mac podman 与 Linux 原生 Docker 上表现不同，最可能出问题的是 /shared 和缓存目录（files 服务写不进去、npx 下载失败）；首次启动重新下载要网络；需要 root 才能做的服务会坏（现在只有 files，没有这个问题）；换用户以后 MCP 服务照样能经网络连后端接口和数据库（D20 写的代价没变），只是读不到密钥、改不了后端的代码与环境了。
